# Technical cross-checks

## Индексируемость одного URL

Зафиксировать по порядку:

1. HTTP-статус и всю цепочку редиректов.
2. Правила `robots.txt` отдельно для `*`, `Yandex` и `Googlebot`.
3. `meta robots` в сыром HTML.
4. `X-Robots-Tag` в HTTP-заголовках.
5. `rel=canonical` и его цель.
6. Данные панели вебмастера, если они доступны и пользователь разрешил их
   использовать.

Различать техническую блокировку и отсутствие URL в индексе. Страница с 200,
разрешённым crawl, без noindex и с self-canonical может ещё не быть
проиндексирована; это не доказанный дефект сайта.

## Дубли карточек в SSR-HTML

1. Использовать сырой HTML ответа, а не гидратированный DOM или Markdown.
2. Считать карточки по устойчивому идентификатору: SKU, slug, `data-offer-id`.
3. В границах каждой карточки проверить видимые название, цену и CTA.
4. Исключить ожидаемые повторы в JSON-LD, hydration payload, `aria-label`, `alt`
   и `title`.
5. Подтверждать responsive-дубль только при двух отдельных видимых DOM-блоках с
   одинаковым содержимым и дополняющими media-классами.
6. Проверить 2–3 страницы, прежде чем назвать проблему системной.

## Сверка стороннего аудита

Для каждого пункта присвоить один статус:

- `confirmed` — доказательство воспроизводится;
- `false_positive` — проверка прямо опровергает вывод;
- `insufficient_evidence` — данных недостаточно;
- `out_of_scope` — пункт не относится к согласованному объекту.

В отчёт включать URL, метод проверки, наблюдение и следующий шаг. Не переносить
приоритет из чужого отчёта без собственной проверки.
