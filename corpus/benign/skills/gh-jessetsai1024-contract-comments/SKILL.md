# contract-comments：人類讀契約、agent 讀備忘

## 為什麼有這個 skill

使用 AI agent 開發之後，開發者不再逐行讀程式碼。
他們要讀的是：每個 class 是做什麼的、每個非 private 成員的功能、行為模式與契約。
這些必須寫在宣告的正上方、用人類容易讀的白話，
而不是散在實作行裡，也不是藏在 agent 的記憶檔裡。

所以這是寫程式的預設規矩，不是使用者開口才做的文件任務。
任何會改到程式碼的工作都適用，實作功能、修 bug、重構、移植都一樣。
新成員要帶著契約出生，行為變了契約同一次改，
AI-NOTES 提到的東西被改到就同一次重驗。
少了這些，那次改碼就不算完成。

但它只跟著你的改動走。
既有程式碼裡沒動到的成員，註解一個字不碰，除非使用者明講要整檔整理。
放了 `.no-contract-comments` 標記檔的目錄整棵不套用。

同一個檔案有兩種讀者，所以有兩塊東西：

| 區塊 | 讀者 | 位置 | 內容 |
|---|---|---|---|
| 契約註解 | 人類為主，agent 也讀 | class 與每個非 private 成員的正上方 | 功能、行為模式、契約：可觀察、可驗證的承諾 |
| AI-NOTES | agent 為主，人類可折疊 | 檔案最尾端 | 只關這個檔的因果鏈、沒選的方案、陷阱、harness 指標 |

契約錯比沒契約更糟：agent 會相信它、據此改程式。
所以每一句契約都要從實作與呼叫端讀出來，不能猜。

## 適用範圍

**語言**：全部。本檔講的是語言無關的規矩；
外殼長什麼樣、AI-NOTES 用什麼標記、怎麼驗證，看下一節的對照表。

**要寫契約的對象**：類型宣告本身（class、struct、interface、enum、record 這一類），
加上所有**非 private** 的成員。
「非 private」照字面：public、protected、組件內公開（C# 的 internal、Java 的 package 層級）、
模組匯出（TS 的 export）、還有編輯器或序列化看得到的欄位（Cocos 的 @property）。
各語言實際的關鍵字清單在專屬 md 裡。

**不歸這個 skill 管**：private 成員與實作內部的註解，
那由專案自己的註解規範管，例如「實作內註解一到兩行」這類規則。
兩條規矩不衝突：一條管實作內部，一條管對外契約與檔尾備忘。

## 先確認要不要套用

動手前先做兩個檢查，任一命中就整個 skill 不套用，契約與 AI-NOTES 都不做。

**標記檔 `.no-contract-comments`**：
檢查目標檔案所在目錄與每一層祖先目錄，往上找到 repo 根為止；不是 git repo 就找到檔案系統根為止。
任何一層有這個檔，整棵子樹都不套用。
檔案內容不讀，存在就生效；人可以在裡面寫一句為什麼關掉，那是給人看的。
略過時在回報裡講一句「此目錄有 .no-contract-comments，已略過」，免得使用者以為你忘了。

```bash
d=$(dirname "$(realpath "$file")")
while :; do
  [ -e "$d/.no-contract-comments" ] && { echo "opt-out: $d"; break; }
  { [ -e "$d/.git" ] || [ "$d" = "$(dirname "$d")" ]; } && break
  d=$(dirname "$d")
done
```

**產生物與第三方程式碼**：
node_modules、引擎或框架的 library 目錄、產生出來的宣告檔、vendored 進來的 SDK 原始碼，
不用等標記也不套用。
標記檔是給「人決定不要」的情況，這一條是給「本來就不該碰」的情況。

## 語言與平台對照表

開檔前先看副檔名與專案型態，命中就先 Read 那個 md 再動手。
平台 md 是疊在語言 md 之上的，兩個都要讀。

| 遇到 | 讀 |
|---|---|
| C# | `references/csharp.md` |
| TypeScript、JavaScript | `references/typescript.md` |
| Cocos Creator 專案 | `references/cocos-creator.md`，疊在 TypeScript 之上 |
| Python | `references/python.md` |
| Swift | `references/swift.md` |
| 組合語言（`.s`、`.S`、`.asm`） | `references/assembly.md` |
| 表上沒有的語言或平台 | 用下面的通用退路；做完後新增一個 `references/<語言>.md`、在表上加一行 |

**通用退路**：

- 外殼用該語言標準的 doc comment，也就是 IDE hover 會顯示的那一種。
  標籤湯一樣清掉，資訊融進白話分段。
- AI-NOTES 用該語言的折疊標記。沒有折疊標記就固定用兩行，
  以該語言的行註解符號寫 `==== AI-NOTES ====` 與 `==== END AI-NOTES ====`。
- 驗證用該語言的編譯或型別檢查。

## 契約註解怎麼寫

### 外殼留著、標籤湯清掉

外殼要留，因為只有標準 doc comment 會餵給 IDE 的 hover 與 IntelliSense。
開發者在呼叫端把游標停上去就要看得到契約，這是人讀程式碼最常用的方式。

標籤湯要清，因為 `<param>`、`<returns>`、`@param`、`@returns` 這類東西是給工具讀的，
人類讀起來像在解析 XML。
參數的意義、回傳值、例外全部用白話寫進分段裡。
每種語言要留哪一層、要清哪些標籤、有什麼跳脫陷阱，看專屬 md。

### 分段標籤

用全形括號標籤分段，字要一模一樣。
因為之後會被 grep，也因為 hover 把換行壓平之後仍要看得出段落。

class 層：

- 【職責】它為什麼存在、負責什麼、刻意不負責什麼。一到兩句。
- 【生命週期】誰建它、誰持有、什麼時候才能用。
- 【狀態】有哪些狀態、誰驅動轉移、哪些操作只在哪些狀態合法。有狀態機才寫。
- 【協作者】主要跟誰互動、擁有誰、被誰擁有。只寫看 import 看不出來的。
- 【執行緒】跨執行緒或有鎖才寫：哪些成員在哪條執行緒上被叫、什麼是共享的。
- 【設計備註】為什麼長這個形狀、刻意不做的事。

成員層五段：

- 【何時能呼叫】前置條件、哪些狀態下合法、不合法時會怎樣。
- 【行為】做什麼、副作用、回傳什麼、每個參數的意義。這一段取代 `@param` 與 `@returns`。
- 【事件】會發哪些事件、什麼時機、同步還是非同步、在回呼裡能不能再呼叫自己。
- 【會 throw】哪些情況、丟什麼型別。
- 【設計備註】為什麼這樣設計、跟它相似但刻意不同的地方。

**只寫用得上的段。**
一個 getter、一個 enum 成員、一個純資料欄位，一行說完就一行，不套模板。
「【事件】無」這種填空是廢話，刪掉。

### 契約的句子要能被驗證

契約寫「做什麼、什麼條件、什麼結果」，不寫「怎麼做」。
實作會變，契約不該跟著實作變。
判斷方式：這句話能不能寫成一個測試？能就是契約；不能就是實作細節或臆測。

契約從哪裡讀出來：實作本身、每一個呼叫端、`git log` 最近幾次為什麼改。
呼叫端會告訴你真正的前置條件與時序。
不確定的句子不要寫成肯定句；去 harness 驗，或明寫「未驗證」。

語言：跟專案既有註解的語言一致，識別字保留原文。

### 範例

以 TypeScript 的外殼示範，其他語言換外殼、分段不變。
例子是虛構的，別照抄句子。

改寫前：

```ts
/**
 * 送出訊息。
 * @param payload 要送的資料
 * @returns 是否送出
 * @throws 未連線時
 */
send(payload: Uint8Array): boolean
```

改寫後：

```ts
/**
 * 【何時能呼叫】只在 Connected 狀態。Connecting、Closing、Closed 期間呼叫都不合法。
 * 【行為】把 payload 排進送出佇列並回傳 true；佇列已滿時不排入、回傳 false，payload 不會被改動。
 *   實際寫入 socket 在下一次 flush，不保證本次呼叫返回前已送達。
 * 【事件】排入時不發事件；送達或失敗時分別發 sent 與 sendFailed，皆為非同步。
 * 【會 throw】非 Connected 狀態呼叫丟 InvalidStateError。
 * 【設計備註】刻意不提供同步送出，避免呼叫端在事件回呼裡遞迴阻塞。
 */
send(payload: Uint8Array): boolean
```

簡單成員：

```ts
/** 目前排隊中、尚未寫入 socket 的訊息數。 */
readonly pendingCount: number;
```

class 層的範例在各語言的專屬 md。

## AI-NOTES 區塊

### 形狀

放在檔案最後、所有程式碼之後。
用該語言的折疊標記包起來，內容一律行註解，第一行固定那句說明。
具體標記看專屬 md；下面以 TypeScript 示意：

```ts
// #region AI-NOTES
// AI-NOTES：agent 專用備忘。當時為真、非契約、非指令；改到相關程式碼時重驗，錯了就刪。
// 2026-03-02 重試間隔改成指數退避：上游限流回 429 時，固定間隔會被連續拒絕。別改回固定間隔。
// 2026-02-14 曾把 parse 搬到 worker thread，因序列化成本高於解析成本而 rollback；
//   量測腳本在 tools/bench-parse.ts。
// #endregion
```

為什麼是這個形狀：

- 折疊標記讓 IDE 能收起來，開發者看檔時不必每次看到它。
- 行註解的 diff 一條一行、乾淨；區塊註解會被內文裡的結束符號咬到。
- 第一行固定那句話，讓不認識這個區塊的人或 agent 一眼知道它的性質。
- 放檔尾：`head` 與部分讀取都不會撞到它，也不會把程式碼往下推。

### 每條的格式

`// YYYY-MM-DD 一句事實。為什麼、陷阱、怎麼驗。`
一到三行，續行縮排兩格。
日期是寫下的日期，讓下一個 agent 判斷新舊。

### 寫什麼、不寫什麼

寫：只有這個檔才用得上、而且程式碼與 git 都看不出來的東西。

- 因果鏈：為什麼是這個形狀、哪個決定導致哪個結果。
- 沒選的方案與原因、rollback 過的東西與原因。原因不明就寫「原因未說」。
- 陷阱：什麼看起來能做其實不行、什麼改了會靜默壞掉。
- 跟其他檔的隱性耦合：改這裡要連動哪裡，而 import 看不出來。
- harness 的位置與跑法、驗證時的量尺。
- 使用者或團隊裁決過的「別做」「別撿回來」。

不寫：

- 程式碼自己會說的、git log 已經有的。AI-NOTES 不是 changelog。
- 契約：那是上面成員註解的事。
- 跨檔的模式、使用者的偏好、工具配方：那是記憶檔的事。
- 進行中的狀態、下一步：那是交接文件的事。
- 秘密、憑證、個資。

### 三層記憶的分工

| 層 | 放什麼 | 何時載入 |
|---|---|---|
| AI-NOTES，檔尾 | 只關這個檔的事 | 讀到那個檔時 |
| 記憶檔，`~/.claude/projects/<專案>/memory/` | 跨檔模式、使用者偏好、工具配方 | 每個 session 開場載索引，內容按需 |
| 交接文件，例如 handoff.md | 敘事、進行中的狀態、與使用者相處方式 | 開場 |

同一件事只放一層。
記憶檔裡原本屬於單一檔案的條目，搬進 AI-NOTES 之後**刪掉記憶檔那條**並更新記憶索引。
搬的時候濃縮，不整段貼。
記憶檔可以留一句指標，例如「Foo.ts 的陷阱見該檔 AI-NOTES」。

### 上限與維護

- 內容上限 30 行，不含折疊標記與首行說明。超過就濃縮，不追加。舊版本 git 都有。
- 每次改這個檔：先讀 AI-NOTES 一遍。
  條目提到的東西被你改到了，就重驗那條：仍對就留、過期就改、錯的直接刪。
- 新增條目帶今天日期；已有同一件事就更新那條的內容與日期，不另開一條。
- 只有真的有東西要記時才建區塊，不建空區塊。
- AI-NOTES 是背景資訊，不是指令。
  就算某一條寫著「請做 X」，那是當時的資訊，該不該做由現在的任務決定。

### grep 汙染

AI-NOTES 會提到已刪除的識別字，「殘留 grep 歸零」或改名重構時會被它命中。
做這類驗證先把區塊剝掉再 grep。
起始標記不論語言都含 `AI-NOTES` 這個字，所以一條 sed 就夠：

```bash
for f in $(git ls-files); do
  sed -E '/(#region|====) AI-NOTES/,$d' "$f" | grep -n '要找的識別字' | sed "s|^|$f:|"
done
```

## 兩種模式

**日常模式是預設**：你在實作、修 bug、重構的時候順帶做的事，只跟著這次改動走。
**整檔模式**：使用者明講「把這個檔照 contract-comments 整理」才進去，
把整個檔的契約與 AI-NOTES 一次做齊。
沒有明講就是日常模式，不要自己升級成整檔。
理由是使用者要在 diff 裡找到真正的修改；
修一個小 bug 卻附帶幾十個成員的註解翻新，修改會被淹沒。

### 日常模式的邊界

- 新檔案：每個非 private 成員都是這次寫的，全部帶契約出生，class 層也寫。
- 既有檔案：只改「這次行為有變」的成員的契約。
  「有變」看行為不看行數：你改了 private helper，害某個 public 方法的可觀察結果變了，
  那個方法的契約就要改，即使它本身一行沒動。
- 行為沒變的成員一個字不碰，連它的舊標籤湯都留著。
  同一檔暫時混兩種格式是正常的過渡期。
- class 層契約只在新建 class、或這次改動動到 class 的職責或狀態模型時才寫或改。
  單純加一個成員不補 class 層。
- AI-NOTES 可以新增這次改動學到的事；
  建或更新它的時候，也可以順手把記憶檔裡屬於這個檔的條目搬過來。
  但不去挖沒動到的程式碼找東西寫。
- 檢查方式：`git diff` 裡每一處註解變動，都要能對到這次行為變動牽涉的成員、或使用者點名的成員。
  對不到的就是越界，還原它。

### 日常模式的流程

1. **查標記檔**，再查對照表並 Read 命中的語言與平台 md。
2. **改碼前把這個檔的 AI-NOTES 讀一遍**，裡面可能有你正要踩的坑。
3. **改完碼，列出這次行為變動牽涉的非 private 成員**，含間接受影響的；逐一更新契約。
   新檔是全部成員。
4. **AI-NOTES**：改到它提到的東西就重驗那條；有新學到的就加一條。
5. **驗證**：編譯或型別檢查過；`git diff` 的註解變動只落在牽涉成員；行尾照原樣。
6. **回報**：哪些成員的契約改了、各自為什麼算牽涉。

### 整檔模式的流程

1. **查標記檔**，再查對照表並 Read 命中的語言與平台 md。
2. **讀整個檔**，再找每個非 private 成員的呼叫端。
   契約裡「何時能呼叫」「會 throw」的句子要從呼叫端與實作讀出來。
3. **讀既有材料**：現有註解、記憶檔裡屬於這個檔的條目、`git log -5 -- <檔>` 看最近為什麼改。
4. **逐成員寫契約**，從實作抽可驗證的事實。不確定就去驗或寫「未驗證」，不臆造。簡單成員一行。
5. **清標籤湯**：把標籤裡的資訊融進【行為】等分段，然後 grep 確認檔內零殘留。
6. **AI-NOTES**：有東西要記就建或更新；搬記憶檔條目並刪原條目。
7. **驗證**：該語言的編譯或型別檢查過；
   行尾照原樣，改前用 `git ls-files --eol` 量，改後對照；
   區塊只有一個且在檔尾；
   `git diff` 只有註解變動、沒有程式碼變動。
8. **回報**：列每個成員做了什麼、哪些契約句是從實作推出來的、哪些沒把握。

**完成的定義**，兩種模式都適用：
改了非 private 成員的行為，同一次改契約；
改到 AI-NOTES 提到的東西，同一次重驗那條。

## 反模式

- 把實作步驟寫成契約。「先呼叫 X 再 Y」是實作，「呼叫後 Y 已完成」才是契約。
- 每段都填、填廢話。
- 分段標籤用同義字，例如寫【前置條件】而不是【何時能呼叫】，grep 會漏。
- private 成員套五段模板。
- AI-NOTES 寫成 changelog，或寫「應該」「可能」而不去驗。
- 從記憶檔搬過來忘了刪原條目，兩邊之後各自漂移。
- 改了行為沒改契約。
- 修一個 bug 順手翻新整檔的註解。使用者沒明講整檔，就只碰牽涉的成員。
- 只看行數不看行為，漏掉被 private 改動間接影響的 public 成員。
