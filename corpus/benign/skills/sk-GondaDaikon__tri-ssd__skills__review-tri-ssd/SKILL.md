# 整合性レビュースキル

<tri_ssd_context>
Tri-SSD: L0(任意メモ docs/l0_ideas/) → L1(要件 docs/l1_requirements/vision.md) → L2(構成 docs/l2_foundation/foundation.md) → L3(フェーズ docs/l3_phases/PH-xxxx.md)。
ID形式: PREFIX-nnnn（REQ, PH, F）。番号は再利用しない（永久欠番）。
配置・分割・粒度の判断に迷ったら `${CLAUDE_SKILL_DIR}/../../docs/layer-rules.md` を読むこと。
</tri_ssd_context>

## 概要

Tri-SSD ドキュメント群の整合性を検証し、進捗を報告する読み取り専用のレビュー。ドキュメントの修正はしない（発見した問題と修正案の提示まで）。

| 検証 | 手段 | 内容 |
|------|------|------|
| ① ID 整合性 | スクリプト（決定的） | dangling 参照・重複定義・status と検証記録の突合 |
| ② 要件の網羅性 | 読み合わせ | どの PH からも参照されていない REQ の検出 |
| ③ 仕様と実装の乖離 | 読み合わせ | 完了済み AC と実装/テストの対応確認 |
| ④ 進捗サマリ | スクリプト＋集計 | PH 別 status・AC/検証記録の進み具合 |

## レビュー時の原則

<avoid_over_engineering>
- 読み取り専用。修正はユーザーの指示があってから（該当スキル・手動編集に委ねる）
- 問題ゼロなら「問題なし」と簡潔に報告する（形式的な指摘を作らない）
- ③の乖離チェックは完了済み（[x]）AC に限定する（未実装の指摘はノイズ）
</avoid_over_engineering>

## 引数

- `$ARGUMENTS` (省略可): 対象フェーズID
  - **省略**: docs/ 全体を検証（③はアクティブな全フェーズが対象）
  - **PH-xxxx**: 指定フェーズを重点検証（①④は全体のまま。②はそのフェーズの `requires` する REQ の対応のみ、③はそのフェーズのみ）

### 使用例

```
/review-tri-ssd                   # 全体の整合性チェック + 進捗サマリ
/review-tri-ssd PH-0002           # PH-0002 を重点レビュー
```

## 実行手順

### Step 1: ID 整合性の機械的検証

共有スクリプトを実行する:

```bash
python3 "${CLAUDE_SKILL_DIR}/../../scripts/validate_ids.py"
```

`python3` が使えない環境（Windows の python3 は Store スタブの場合がある）では `python` / `py`。スクリプトが使えない場合は Grep で `REQ-\d{4}` / `F-\d{4}` / `PH-\d{4}` を検索し、参照と定義（見出し行）を手動で突合する。

文書間の依存関係を俯瞰したい場合は `python3 "${CLAUDE_SKILL_DIR}/../../scripts/doc_graph.py" --format mermaid`（全体図）や `--focus <ID>`（特定 ID の近傍）が使える。

検出対象:
- **dangling 参照**: 定義が存在しない ID への参照（例: 削除済み REQ を指す「対応REQ」）
- **重複定義**: 同一 ID が複数箇所で定義されている
- **status 突合**: `status: done` の PH に PASS 未記録の F がある（警告）

### Step 2: 要件の網羅性（読み合わせ）

1. L1 の全 REQ を列挙
2. 各 REQ について、いずれかの PH（`_archive/` 含む）の「対応REQ」または frontmatter `requires` に現れるか確認
3. どこからも参照されていない REQ を「未計画の要件」として報告（エラーではなく情報。意図的な後回しかを確認する）

### Step 3: 仕様と実装の乖離（引数省略時はアクティブ全フェーズ、PH 指定時はそのフェーズ）

完了済み（`[x]`）AC を対象に:
1. `検証:` 行のテスト名・コマンドが実在するか（Glob/Grep でテストファイル・スクリプトを確認）
2. 検証記録の PASS と AC チェック状態が矛盾していないか
3. L2 の「確認済みの前提」と実装が食い違っていそうな箇所があれば指摘（深追いはしない）
4. L2 の分離ファイル（`docs/l2_foundation/interface.md` / `data.md`。存在する場合）も乖離チェックの対象に含める（画面 ID・エンティティと実装の対応）

### Step 4: ドキュメント衛生（軽く）

1. **未解決の分離ポインタ**: foundation.md に「（未作成）」のまま残っている `interface.md` / `data.md` への骨子ポインタがあれば報告（→ `/gen-interface` / `/gen-data` を案内）
2. **サイズ超過**: docs/ 配下で300行を超えるファイルを報告し、layer-rules のファイル分割ルール（トリガー⑤）に基づく分割を提案
3. **検証されない印**: L2 に `（未確認・要検証）` のまま（検証場所未確定）の印が残っていれば報告（→ `/gen-l3` で振り分け）

### Step 5: レポート出力

```markdown
# Tri-SSD 整合性レビュー結果

## ① ID 整合性
（validate_ids.py の出力。エラー0件なら「問題なし」）

## ② 要件の網羅性
- 全 REQ: n件 / PH に紐付け済み: n件
- 未計画: REQ-xxxx「[名前]」（どの PH にも現れない）

## ③ 仕様と実装の乖離
（問題があった AC のみ列挙。なければ「乖離なし」）

## ④ 進捗サマリ
| PH | status | F PASS | 備考 |
|----|--------|--------|------|
| PH-0001 | done | 3/3 | アーカイブ可能 |
| PH-0002 | in_progress | 1/2 | F-0005 未実装 |

## 推奨アクション
- （例: PH-0001 は `/archive-l3 PH-0001` でアーカイブ可能）
- （例: REQ-0007 が未計画。`/gen-l3` で追加するか、やらないなら L1 の「やらないこと」へ）
```

## 完了後の案内

- エラー・警告の件数と要点を報告
- 修正が必要な場合は、どのスキル（gen-l1 / gen-l3 / gen-code）または手動編集で直すべきかを案内
- 全フェーズ完了が確認できたら `/archive-l3` を案内

## エラーケース

| ケース | 対応 |
|--------|------|
| docs/ が存在しない | エラー: 「Tri-SSD ドキュメントが見つかりません。`/init-tri-ssd` を先に実行してください」 |
| L3 が1件もない | 情報: ①のみ実行し、「フェーズ未作成。`/gen-l3` で作成できます」と案内 |
| 指定した PH-ID が存在しない | エラー: 「指定されたフェーズが見つかりません」 |
