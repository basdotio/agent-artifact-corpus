# niri configuration

Read this before changing keybindings, window or layer rules, blur, animations,
outputs, workspaces or anything else in `~/.config/niri/`.

Upstream reference: the niri wiki at https://github.com/niri-wm/niri/wiki
(source in `docs/wiki/` of https://github.com/niri-wm/niri). Version tags
below ("niri 25.11") are the release that added the feature. Check the
installed version with `niri --version` before using anything new.

## Where the config lives

niri reads `$XDG_CONFIG_HOME/niri/config.kdl` (normally `~/.config/niri/config.kdl`),
then `/etc/niri/config.kdl` as a fallback. `niri -c <path>` or `$NIRI_CONFIG`
point somewhere else. The format is KDL: `//` comments a line, `/-` in front
of a node comments out the whole section.

A typical DMS setup looks like this:

```
~/.config/niri/
├── config.kdl          # yours: input, layout, rules, binds, startup
└── dms/                # written by DMS, included from config.kdl
    ├── colors.kdl
    ├── layout.kdl
    ├── alttab.kdl
    ├── binds.kdl
    ├── outputs.kdl
    ├── cursor.kdl
    ├── input.kdl
    └── windowrules.kdl
```

## Includes (niri 25.11+)

`include "file.kdl"` works only at the top level. Paths are relative to the
including file; absolute paths work too, `~/` paths since niri 26.04.
`include optional=true "file.kdl"` (niri 26.04) does not fail when the file is
missing. All included files are watched and trigger a live reload.

Includes are positional. What matters in practice:

- Normal sections merge. A later `layout { gaps 8 }` only changes gaps.
- An include overrides values set before it. Values set after it override the include.
- `binds` from a later file replace earlier binds on the same key.
- Multipart sections (`window-rule`, `layer-rule`, `output`, `workspace`) are
  inserted at the include position without merging. Window rules apply in
  order, so later rules win for the same property.
- Some sections replace instead of merge: each animation inside
  `animations {}`, `struts`, `preset-column-widths`, pointer device sections in `input`.
- In an included file, an empty `layout { border {} }` does nothing. In the
  main file it turns the border on. Add `on` explicitly when moving border
  settings into an included file.

To see where a value really comes from, read the include lines of
config.kdl from top to bottom.

## Files DMS writes into ~/.config/niri/dms/

| File | Comes from | Edit by hand? |
|------|-----------|---------------|
| `colors.kdl` | matugen niri template, on every theme or wallpaper color change | No. Override after the include, or drop the include. |
| `layout.kdl` | DMS settings `niriLayoutGapsOverride`, `niriLayoutRadiusOverride`, `niriLayoutBorderSize` and the corner radius window rule | No. Change the DMS setting. |
| `alttab.kdl` | `recent-windows` highlight radius | No |
| `cursor.kdl` | DMS cursor settings | No |
| `input.kdl` | DMS keyboard settings (repeat, layout tracking, numlock) | No |
| `outputs.kdl` | DMS display page, rewritten when the user saves there | Only if the user does not use the DMS display page |
| `binds.kdl` | `dms setup binds` defaults plus edits from the DMS keybinds page or `dms keybinds set niri ...` | Prefer `dms keybinds` |
| `windowrules.kdl` | DMS window rules page, `dms config windowrules ...`, the floating rule for DMS windows | Prefer the DMS page or CLI |

`dms setup <name>` creates a missing or empty file with defaults and never
overwrites content (`dms setup headless --force` does, with backups). Files
with a `// ! DO NOT EDIT !` header are regenerated by the running shell.

Check that a file is actually included:

```bash
dms config resolve-include niri binds.kdl     # {"exists":true,"included":true}
```

Put your own overrides in config.kdl after the DMS include lines, or in your
own file (for example `custom.kdl`) included last. Both survive DMS rewrites.

## Key bindings

Upstream: Configuration:-Key-Bindings.

```kdl
binds {
    Mod+E hotkey-overlay-title="Files" { spawn "nautilus"; }
    Mod+Shift+S { spawn-sh "grim -g \"$(slurp)\" - | wl-copy"; }   // spawn-sh: niri 25.08+
    XF86AudioRaiseVolume allow-when-locked=true { spawn "dms" "ipc" "call" "audio" "increment" "3"; }
    Mod+Q repeat=false { close-window; }
    Mod+WheelScrollDown cooldown-ms=150 { focus-workspace-down; }
}
```

- `spawn` does not use a shell: every argument is its own string. Use
  `spawn-sh` (25.08+) for pipes, variables or `~`.
- The same key twice in one file is a parse error. Across includes the later one wins.
- `binds {}` has no defaults. Never delete the section.
- `hotkey-overlay-title=null` hides a bind from the overlay (`Mod+Shift+Slash` by default).
- See every action: `niri msg action --help`.

Before binding a key, list what is bound and where it comes from:

```bash
dms keybinds show niri | jq '.binds[][] | select(.key=="Mod+E")'
```

Tell the user what a key did before you replace it. `dms keybinds set niri`
writes to `dms/binds.kdl`:

```bash
dms keybinds set niri "Mod+E" "spawn nautilus" --desc "Files"
dms keybinds set niri "Mod+Q" "close-window" --no-repeat
dms keybinds remove niri "Mod+E"
```

DMS functions are bound through IPC, for example
`spawn "dms" "ipc" "call" "spotlight" "toggle"`. Find the target with
`dms ipc list`.

## Window rules

Upstream: Configuration:-Window-Rules.

Find the app id and title first: `niri msg pick-window` (click the window) or
`niri msg --json windows | jq '.[] | {app_id, title}'`. Matchers are regular
expressions that match anywhere, so anchor them.

```kdl
window-rule {
    match app-id="^org\\.mozilla\\.firefox$"
    open-on-workspace "browser"        // needs a named workspace
    default-column-width { proportion 0.66; }
}

window-rule {
    match app-id="^pavucontrol$"
    open-floating true
}

window-rule {
    match is-active=false
    opacity 0.92
}

window-rule {
    geometry-corner-radius 12
    clip-to-geometry true
}
```

Opening properties (`open-on-workspace`, `open-floating`,
`default-column-width`, ...) apply once when the window opens. Dynamic
properties (`opacity`, `geometry-corner-radius`, `block-out-from`, ...) apply
continuously. DMS's own windows (Settings, Notepad, Polkit, process list) use
app id `com.danklinux.dms`.

DMS also lists rules from all your files as JSON, which is handy for review:
`dms config windowrules list niri`.

## Layer rules (niri 25.01+)

Upstream: Configuration:-Layer-Rules. Layer rules target layer-shell surfaces
(bars, launchers, wallpapers, notifications) by namespace. List namespaces
with `niri msg layers`. DMS uses `dms:` namespaces such as `dms:bar`,
`dms:dock`, `dms:control-center`, `dms:spotlight`, `dms:notification-popup`,
`dms:osd`, `dms:desktop-widget:<plugin id>`. The DMS wallpaper surface uses
`quickshell`, the blurred wallpaper `dms:blurwallpaper`. Full list:
https://danklinux.com/docs/dankmaterialshell/layers

```kdl
// Keep the clipboard history out of screencasts
layer-rule {
    match namespace="^dms:clipboard$"
    block-out-from "screencast"
}
```

## Workspaces, overview and the wallpaper

Since niri 25.05 each workspace has its own background. Surfaces on the
background and bottom layers move and zoom with workspaces; top and overlay
layers stay on screen. Put bars on the top layer.

To keep a wallpaper still while switching workspaces, put it into the
backdrop and make workspace backgrounds transparent:

```kdl
layer-rule {
    match namespace="^quickshell$"     // DMS wallpaper surface
    place-within-backdrop true         // niri 25.05+, background layer only
}
layout {
    background-color "transparent"
}
```

DMS's generated config already sets both (`background-color` in
`dms/colors.kdl`). `place-within-backdrop` works only for background layer
surfaces that ignore exclusive zones, and surfaces in the backdrop get no
input at all. DMS desktop widgets sit on the bottom layer, so they move with
workspaces and cannot be pinned this way.

## Blur and other background effects (niri 26.04+)

Upstream: Window-Effects and the `blur {}` section in Configuration:-Miscellaneous.

```kdl
window-rule {
    match app-id="^kitty$"
    opacity 0.9                      // or set transparency in the app itself
    background-effect {
        blur true
    }
}

layer-rule {
    match namespace="^dms:bar$"
    background-effect {
        blur true
    }
}
```

The surface must be semitransparent or the effect is hidden. Xray (blur of
the wallpaper only) is on by default when blur is on and is much cheaper than
`xray false`. Blur on niri versions before 26.04 does not exist; the config
will fail to parse.

## Animations

Upstream: Configuration:-Animations.

```kdl
animations {
    // off                 // all animations off
    slowdown 1.5           // >1 slower, <1 faster
    window-open {
        duration-ms 200
        curve "ease-out-expo"
    }
    workspace-switch {
        spring damping-ratio=1.0 stiffness=800 epsilon=0.0001
    }
}
```

Each animation block replaces the whole block from earlier files, so copy
all its settings when overriding. `window-open`, `window-close` and
`window-resize` accept a `custom-shader` (GLSL); shader compile errors go to
the niri log, not to `niri validate`.

## Outputs

```bash
niri msg --json outputs | jq 'to_entries[] | {name: .key, make: .value.make, model: .value.model, modes: [.value.modes[] | "\(.width)x\(.height)@\(.refresh_rate/1000)"]}'
```

```kdl
output "DP-1" {
    mode "2560x1440@165.000"
    scale 1.25
    position x=0 y=0
}
```

If `dms/outputs.kdl` is included, DMS owns output settings. An `output` block
for the same monitor in your own file as well can fail to parse or be
ignored, so pick one place. `niri msg output <name> ...` changes an output
until the next reload, which is useful for trying a mode before writing it.

## Validate and reload

```bash
niri validate                     # parse ~/.config/niri/config.kdl and all includes
niri validate -c /path/to/test.kdl
niri msg action load-config-file  # reload now instead of waiting for the file watcher
```

niri reloads on every save. A config that fails to parse is not applied; niri
keeps running with the previous config and shows a red "Failed to parse the
config file" notice. Fix the error, save again, and the notice goes away.
After editing, always run `niri validate` and report its output.

Logs: `journalctl --user -u niri -b` when niri runs as the systemd user unit
(`niri-session`), otherwise wherever the display manager sends its output.
