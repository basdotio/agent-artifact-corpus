# Drexify a repository

Map every place a codebase makes a semantic judgment, report the whole picture first, then move sites to Drex one at a time. The scan is useful on its own. Implementation is paced to the repository's conventions and deployment constraints.

## Use with drex-for-harness

This skill decides where Drex fits. The `drex-for-harness` skill covers how to call it: question design, the request contract, credentials, the bundled helper, and verification. Load it before designing questions or writing a call. If it is not installed, read the live Drex docs at `https://drex.nace.ai/docs/drex` before writing any integration, and do not guess fields, model ids, or limits.

Whether Drex is the user's default decision provider is decided by the provider preference rules in `drex-for-harness`. When Drex is the default and a Drex call fails, times out, or has no key, new decision code must not call another model provider. It raises, returns an explicit failure, or uses a documented safe default such as keeping the original order, and it logs the failure. Keeping the existing provider path behind an explicit configuration switch is allowed, because a person selects it. Sending a successful low-confidence Drex answer to a reasoning model or a person through a reviewable threshold is an escalation branch, not a fallback, and is allowed in either mode.

## The bundled script

`scripts/drexify.py` sits next to this file. Resolve it relative to the real location of this SKILL.md, not the current directory. It needs Python 3.9+, uses only the standard library, reads files, and never calls a model or the network.

- `python3 "<skill-dir>/scripts/drexify.py" scan --repo <root> --save <map.json>` searches the whole repository once for decision signals, in under a minute on a large repository. It prints a short map of areas and balanced groups, one per suggested helper, and writes the full map to `<map.json>`. An area too big for one helper is split by folder. Use the suggested number. Add `--groups <N>` only when the user asks for a specific number. Test folders (`tests`, `test`, `__tests__`, `spec`, `specs`, `testing`, `testdata`, `e2e`, `e2e-tests`, and `src/*Test` source sets, in any case), fixtures, and `example`, `examples`, `sample`, `samples`, `cookbook`, or `cookbooks` folders are skipped. So are test and story file names such as `test_*.py`, `*_test.go`, `*.test.ts`, `*.spec.ts`, `*.vitest.ts`, `*.e2e.ts`, `*.clienttest.tsx`, `*.stories.tsx`, `*Test.java`, `*Tests.cs`, Django's `tests.py`, and Rust's `tests.rs`. Vue and Svelte files are scanned. `--include-tests` scans all of them. An `eval`, `evals`, `evaluation`, or `evaluations` folder inside a test folder is still scanned, except under a source-set test root such as `src/test`. Database migrations are always skipped: `alembic`, `migrations`, and `flyway` folders in any case, `db/migrate`, `db/migration`, and `src/migration`. Git submodules are not scanned. Name them as unscanned in the coverage line if they hold product code.
- `scan --from <map.json> --group <K>` prints group K from the saved map instantly, without searching again. The first line gives the group's totals: files, candidate functions, and files without one. Each file is followed by its candidate functions as `path:line  name  [signals]`. `--area <name>` prints one area. An area ending in `/*` means only the files directly inside that folder. It warns when the repository changed since the map was saved. When the harness cuts long command output, add `--out <file>` with a file outside the repository: it writes the full listing there and prints only its first line, so you can read the file in parts.
- Candidate functions are functions that call a model, Drex, a reranker, or fuzzy matching, functions that call the repository's own model wrappers, and decision-named functions that use labels, regexes, keyword rules, model wording, embedding similarity, or a same-file helper with one of those signals. Model calls include moderation, language identification, class probabilities such as `predict_proba`, an injected `callLlm` function, a judge or evaluator agent's `run`, and an interface method whose prompt is an `@UserMessage` or `@SystemMessage` annotation. The `decision-api` signal marks the decision API request shape (`/v1/systemone`, `noul`, or a `decisionModel.decide` call) on any host, and `drex` marks the Drex host or SDK. A class named like `JudgeClient` or `Bot` that is defined beside a model or decision API call, or any class defined beside a `decisionModel.decide` call, is learned as a client, and code that constructs or calls it, such as `Bot.as(...)`, is marked too. `output_pydantic` and `output_json` on a task count too, and so does a function that calls a same-file helper which builds that task. An `is`, `should`, `can`, or `has` predicate that tests a keyword loop or passes a tuple of labels into a call is included. So are agent and scorer judges (a `judge:` block or structured agent output), `ChatClient` prompt chains, sentiment word-list libraries, keyword checks in Java streams and lowercased `any(word in text.lower() ...)` checks in Python, a loop that runs a list of regex patterns against one text, and a `run` or `evaluate` method on an Evaluator, Ranker, Router, Classifier, or Judge class whose other methods call a model. A function whose only signal is the word rerank or cross-encoder is left out when it is a constructor, an accessor, `toString`, or `build`, or when its body is under four lines and calls no reranker, because that is configuration. Wrappers are learned from files that import a model library, then from public functions named for a model, such as `send_message_to_model`, that call those wrappers, up to three layers. The list is a checklist, not the answer. Some candidates are not decisions, and some decisions are not listed.
- `python3 "<skill-dir>/scripts/drexify.py" check <report> --repo <root> --fix` checks a written report: the headline counts, the statuses, duplicates, every `path:line` pointer, and the coverage line after the list. `--fix` rewrites a shortened path only when it matches exactly one file, and moves each site pointer to the first line of the function it sits in. Use `-` as the report to read it from standard input without writing anything.

If the script is missing or cannot run, do the same steps by hand.

## Scan the repository

1. **Map.** Run `scan --save` once, with the map file outside the repository (for example in the system temp folder). If the session cannot write that file, helpers use `scan --repo <root> --groups <N> --group <K>` instead, which repeats the search.
2. **Split when it pays.** If the scan prints one group, or helpers are not available, scan alone, because one agent is cheaper. Otherwise give each helper one group. Pass it the exact command `python3 "<skill-dir>/scripts/drexify.py" scan --from <map.json> --group <K>` with absolute paths. Tell it to record only sites whose decision function is inside its group. It may search the rest of the repository for callers of a function, but not for new sites.
3. **Check every candidate function.** Open the lines of each one, enough to see what it returns. Decide whether it is a site using the rules below. This fixed checklist is what keeps two scans of the same code close.
4. **Then look past the list.** For every flagged file without a candidate, open the hit lines the scan prints for it. In those files, in the candidates' files, in functions that call a candidate or that a candidate calls, and in other classes in a site's folder or its subfolders that implement the same interface or base class, look for decisions the scan cannot see. Do not browse other unflagged parts of the repository for new sites. Look for: keyword rules that are not a short loop over the phrases, decisions made through an agent or request object built in one file and run in another, and choices the model makes by filling a tool argument from a fixed set of labels.
5. **Return a fixed format.** Each helper returns three parts and nothing else: the site lines in the format below, a `## Not counted` section with any dead code or fixed logic worth noting, and one coverage line that sorts every candidate, such as `Checked 212 of 212 candidate functions: 48 sites, 61 callers, wrappers, or backends, 99 not decisions, 4 dead. Opened 95 of 95 files without one and looked around the candidates: 6 more sites. 54 site lines in total.` The total must equal the number of site lines returned. Each candidate goes in exactly one bucket. A site's own helpers, such as its question builder, request builder, reply parser, or a constructor that sets its question, go under callers, wrappers, or backends. When more than one fits, dead comes first, then sites, then callers, wrappers, or backends, then not decisions.
6. **Wait for every helper.** Do not write the report until every helper has returned its result. If the agent only delivers helper results after the turn ends, end the turn with a short status and write the report when the results arrive. If a helper fails, rerun its group or scan that group yourself. A report built from some groups is not a scan of the repository.
7. **Merge and check.** Combine the lines, remove duplicates, write the report to a file, and run `check --fix`. Fix every remaining problem and rerun until it prints `ok`. Run it on the exact file you deliver, after your last edit, including the plan. A passing draft does not count. `--fix` edits only the report file, never the repository. If the session cannot run it on a file, pipe the complete final text, plan included, to `check -` and apply the reported fixes yourself.

Start every helper on a cheaper, faster model, and name that model explicitly when starting it, because some agents give helpers the lead's model by default. Keep the strongest model for merging, judging fit, and writing the plan.

## What counts as one site

Counting must be mechanical, so two scans of the same code give the same number. The backend, wrapper, generation, and dead-code rules below come before the rule that the site holds the model call.

- **One site is one decision function:** the function or method whose return value is the judgment, meaning a label, a yes or no, a pick from a set, or an ordered level.
- When a judgment passes through several functions, the site is the function that contains the model call, Drex call, or rule, even when a caller is the one on the candidate list. A shared client function that only sends requests for several different judgments is a wrapper. Each function that builds its own question for it is a site. The same holds when the questions come from the user's configuration: a shared helper that sends prepared checks and returns the answers is a wrapper, and each function that frames its own input and acts on the answer, such as an input guardrail and an output guardrail, is a site. When the model call or decision client is passed in, such as an injected `callLlm`, the site is the shared function that builds the question, makes the passed-in call, and reads the answer. Each caller that only supplies the call is a caller. When the question is written in one method, such as a constructor, and asked in another, the site is the method that returns the judgment, and the constructor is an extra pointer. A shared base-class runner is a wrapper too. Each subclass that sets its own question is a site, pointed at its method that returns the judgment.
- Its callers, prompt, schema, parser, and settings are extra pointers on the same line, not new sites. Parsing the model's reply, for example a PASS or FAIL string, is part of the same site.
- Judgments stored as data, such as evaluator templates, question sets, or a prompt catalog, are not sites one entry at a time. The site is the function that runs them and returns the judgment. Name the catalog as an extra pointer on that line. A runner that sends a question the user wrote to a model is a site when the product itself acts on the answer, such as storing a score or blocking a message. A library runner that only returns the answer to the caller's own code, such as one behind a decision interface the user declares, is a wrapper: the site is in the caller's code, outside the library.
- A rule the user configures explicitly, such as a keyword list, a regex, or a match-all-words setting picked in the product, is the user's chosen fixed logic, not a site. When the product also offers a model-based option for the same choice, that option is the site.
- The same judgment in two different functions is two sites only when each function makes its own model call, Drex call, or rule, because each one migrates separately. Sync and async twins follow the same rule: before finishing, check each site for a twin such as `route` and `routeAsync`, and list each twin that makes its own call on its own line. A function that gets the judgment by calling another site is a caller, not a site.
- Interchangeable implementations of one interface, such as a `rerank` or `classify` method on each provider class, are backends, not sites. The site is the code that calls the interface and acts on the result. List the backends as extra pointers on that line.
- A function that mixes fixed logic with a keyword guess on free text is a site, because of the guess.
- Language identification whose label the code branches on or stores for rules, such as routing or right-to-left display, is a `choice` site. A language code passed only to a translation call is part of that generation.
- A model call whose main output is generated text, a plan, or extracted data is generation, even when it also returns a flag. It is a site only when the judgment is the main thing the code acts on. A reply that is used whichever way the flag goes is generation. Detection that rewrites the text by default, such as redaction, is generation. Detection that blocks, routes, or rejects by default is a site. Tags or labels the model writes freely, with no fixed set to choose from, are generation. Picking from a fixed or stored set of tags is a site.
- To test a call that both judges and produces something, imagine Drex answering only the judgment. If the code still needs the generated or extracted value on the path it takes, the call is generation. Examples: an add-or-update decision that also writes the memory text stored either way, a time filter whose main output is a date window, a query rewrite that also returns a flag. Parsing dates, durations, amounts, or time windows out of text is extraction, also when it uses keyword rules.
- An agent planner that returns either a tool call with generated arguments or a final reply is generation. Picking from a fixed set of tools or routes is a site only when the code acts on the pick alone, such as a router whose routes take no generated input. A tool that only carries out a choice the planner already made, such as adding a label or handing off, is part of that planner, not a site.
- One model call that returns several judgments at once is one site. Give the shape of the judgment the code acts on first, and name the others in the note.
- In scope: production code and evaluation code. Out of scope: tests, fixtures, notebooks, examples, templates, starter projects, generated code, vendored code, database migrations, and archived code kept only for reference, such as an `archive/` folder.
- Out of scope: text generation, chat, summarization, embeddings, and fixed logic. Fixed logic includes thresholds on measured numbers (lengths, counts, scores), also when the score compares two texts, such as edit distance, token overlap, or recall. It also includes schema checks, exact lookups, and patterns that recognize a format, such as a number, date, currency, ID, or markup syntax. Rules over formal input, such as shell commands, source code, error messages, file names, or model ids, are fixed logic too. A keyword list or pattern matched against free natural-language text to guess its meaning, such as intent, topic, tone, or document type, is a site. A number computed from text overlap is a measured number, not a guess, even when the code ranks by it or cuts off at it: BM25, token or n-gram overlap, and embedding distance used as a weight or a ranking are fixed logic, also when Drex could rank better. Embedding similarity that picks a label from a fixed set is a classifier, so it is a site.
- Functions with no callers are not counted, and neither are functions reached only from them. Search for the callers of every site before listing it, including model clients, rerankers, and classifier methods. A method reached only from a warm-up, a helper marked unused or deprecated, or commented-out code is dead. Mention them in a separate note. Being public does not make a function called, and neither does a call from tests. A branch or strategy that no production caller can select is dead too. Code that cannot run as checked in, for example because it imports a module missing from the repository, is not counted either. The one exception is a published library, where outside users are the callers. Entry points count as called: HTTP handlers, queue or workflow activities, CLI commands, and scheduled jobs.

## Pick the status

Use the first status that is true. Use only these four. The headline lists them in a different, fixed order.

1. **implemented now:** this session changed the site to Drex and verified it.
2. **already on Drex:** Drex runs on the default path, all the way from the product's entry point. The default path is what runs with the code's own default values, ignoring environment variables, flags, settings files, and deployment configuration.
3. **partial:** Drex code exists for this site, but it is off by default, behind a flag or setting, one of several paths, or the default only inside a path that is itself not the default.
4. **candidate:** no Drex code exists for this site.

Drex code means any code that calls the Drex API, whatever the client is named: the Drex host `drex.nace.ai`, or a server the repository documents as self-hosted Drex. Look for the host, not only the word Drex. Other providers serve the same decision API shape, so the `/v1/systemone` path, `noul` questions, or a decision-model interface do not show Drex alone. Read the base URL the code uses by default. A decision API on another host, or another decision-model SDK, is the existing mechanism: the site is a candidate, and its note says that it already sends decision questions, so the move is mostly the host, key, and model id.

Pick the shape from the branch the code takes: `noul` for yes or no, `choice` for one of a fixed set, `score` for an ordered level. `choice` returns exactly one option. When the code keeps a subset, such as every relevant section or every matching source, use one `noul` per candidate, sent as several questions in one request. A numeric rating, such as 0 to 10, maps to `score` with named levels. A reranker or relevance score maps to `score` with concrete relevance levels, or to `choice` when only the top candidate is used.

## Report the summary

Write the headline with all four counts in this order, then one line per site grouped by product area:

```text
Your repo has been scanned. Identified 5 sites of drexification (1 already on Drex, 1 partial, 1 implemented now, 2 candidates). Below is the list of processes:

- Document splitting (`src/ingest/split.py:42`): already on Drex, choice over document types.
- Document classification (`src/ingest/classify.py:88`): implemented now, choice over 11 section types, behind `USE_DREX_CLASSIFY`.
- Search passage filter (`src/search/filter.py:64`): partial, noul per passage, Drex only when `DREX_URL` is set.
- Template selection for the task (`src/tasks/templates.py:51`): candidate, choice over template ids, also `src/tasks/api.py:30`.
- Audit policy identification (`src/policy/match.py:120`): candidate, noul per policy.

Checked 61 of 61 candidate functions: 4 sites, 22 callers, wrappers, or backends, 34 not decisions, 1 dead. Opened 12 of 12 files without one and looked around the candidates: 1 more site. 5 site lines in total. Read `src/ingest`, `src/search`, `src/tasks`, and `src/policy` in depth.
```

With one site, write `1 site`, `1 candidate`, and `1 site line in total`. A bucket of one can read `1 caller, wrapper, or backend` or `1 not a decision`. `check` accepts both forms.

- Each site line is `- <process> (`<path:line>`): <status>, <shape>, <short note>.` The pointer is the first line of the decision function, its `def` or signature line. A class line is allowed when the class itself is the decision.
- Write every pointer as a full path from the repository root, even when it repeats a heading. Do not shorten with `...`, brace groups, or bare filenames.
- Counts must match the list, including zeros.
- After the list, add the coverage line in the same format helpers return, followed by which parts of the repository were read in depth or only sampled. With helpers, add up their buckets. `check` requires it right after the list and checks its numbers: `N site lines in total` must equal the site lines in the final list, and checked can never exceed the total. The buckets may add up to more than N when duplicates were removed. Say so, for example `After removing 2 duplicates, 52 site lines in total.`
- Put anything outside the four statuses, such as dead code or sites that should stay fixed logic, under a heading on its own line that starts with `Not counted`, for example `## Not counted`. `check` verifies pointers there but does not count them. The section ends at the next heading of the same or a higher level, so its subheadings stay uncounted. Put the implementation plan after the list under a heading that starts with `Plan` or `Implementation plan`, such as `## Plan`, which is not counted either. Headings above the headline and lines inside code blocks never change what is counted.
- Mark a site implemented only when it was changed and verified in this session. Never report planned work as done.
- If the user or repository requires another report format, put the summary inside that format instead of replacing it.
- For a large list, write it to a file the user can review and keep the chat reply to the headline and top candidates.

## Pace the work

- The scan and summary are a complete deliverable. They do not require implementing every site in one pass.
- In plan mode or a read-only session, change nothing in the repository: scan, write the summary and the plan, and stop before implementing. The map, the report, and `check --fix` stay allowed when their files are outside the repository, such as in the system temp folder or the harness's plan file. If the session cannot write any file, use `check -`. Present the plan in the harness's own plan format when it has one, such as a plan file or a plan tool. Otherwise put it after the list under `## Plan`. The scan and the plan may name shapes without the live Drex docs. Read the docs before writing request bodies, choosing a model, or changing code.
- When implementing, change one site or one group of closely related sites at a time, and follow the repository's branch, review, size, and test conventions. When the user asks for several sites, finish, test, and report each group before starting the next. Start with high-fit, low-risk sites unless the user sets the order.
- Respect deployment constraints and note them per site. Workflow engines with deterministic replay (for example Temporal) need Drex calls inside activities, not workflow code. A per-keystroke, per-line, or per-token path usually cannot afford a network round trip. Measure it, say so, and keep the switch off by default. Self-hosted, air-gapped, or customer-hosted deployments may need the self-hosted backend or the existing provider path kept available. Gate new paths with the repository's existing configuration or flag mechanism when one exists.
- On a re-scan, update the existing list and keep pointers stable rather than starting over.

## Implement one site

1. Design the questions with `drex-for-harness`. Keep the current mechanism's labels or outputs so callers do not change.
2. Put the new path behind the repository's configuration mechanism unless the user asks for a direct switch.
3. Compare Drex against the current mechanism on representative examples before recommending a default. Report accuracy, latency, and cost only from runs that actually happened. The baseline is the current mechanism's real output on the same inputs. When the current code ranks or filters by another signal, such as embedding similarity or full-text search, run that signal. A hand-written, fixed, or random order is not the current mechanism. When the current mechanism cannot run, for example because no provider key is available, report the comparison as not run. Never print or report a baseline number that the comparison did not compute.
4. Decide and state what happens when the Drex call fails, times out, or has no key: which path runs, and whether it is an error, a logged safe default, or the existing mechanism. The existing mechanism is allowed only outside default mode or behind an explicit switch. Test that path. Report it per site, and do not describe every site with one sentence unless each was checked.
5. Update the site's status in the summary, rerun `check`, and report what was changed and tested.

Do not change production routing, credentials, or unrelated code without authorization.
