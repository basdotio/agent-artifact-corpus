# 内容构筑：把卡"写好看、玩得动"

变量机制是骨架，内容质量决定卡的上限。本文件给写作规范与结构模板。

## 1. 角色卡字段各自该放什么

| 字段 | 放什么 | 写作要点 |
|---|---|---|
| `name` | 卡名 | 与文件名/世界书名一致，避免重名 |
| `description` | 角色描述（人设主体） | 现代写法常把人物卡（外貌/性格/背景/关系/行为准则）都写这里，用 `【】` 或小标题分区；**不写与剧情无关的元信息** |
| `personality` | 性格摘要 | 可留空（很多作者并入 description）。写"性格标签"式短句 |
| `scenario` | 场景 | 当前时间/地点/局面的一句话设定 |
| `first_mes` | 开场白 | **只写这一场戏**：环境 + 角色的动作/对话 + 给玩家的钩子；200~500 字通常最佳；变量卡在结尾追加 `<UpdateVariable><initvar>…</initvar></UpdateVariable>`（正式开局若在 alternate_greetings 里则写那里） |
| `alternate_greetings` | 多开局 | 每个开局一个不同情景（同一角色不同切入），每个都可自带 `<initvar>` 块 |
| `mes_example` | 对话示例 | 用 `<START>` 分隔几组 `{{user}}: … / {{char}}: …`；**示例是给 AI 的语音风格模板**——写你希望 AI 模仿的对白风格（含口癖、称呼、动作描写密度），不要写剧情大纲 |
| `creator_notes` | 作者备注 | 玩法说明、命令、致谢；也会展示给玩家 |
| `system_prompt` / `post_history_instructions` | 尽量留空 | 卡内越少覆盖全局预设越好（除用户特别要求） |

## 2. 世界书条目组织（照抄示例卡的结构）

用**分隔条**把世界书按区组织（禁用状态的 `===X开始===` / `===X结束===` 条目），既有分区视觉效果又零成本：

```
===角色开始===
  角色详情        （蓝灯 @Character After——常驻人物卡）
  角色阶段        （蓝灯 @D0——按变量的阶段行为，配合 EJS/规则）
===角色结束===
===变量开始===
  [initvar]变量初始化勿开   （禁用）
  变量列表                  （蓝灯 @D0）
  [mvu_update]变量更新规则  （蓝灯 @D0）
  [mvu_update]变量输出格式  （蓝灯 @D0）
===变量结束===
===世界开始===
  世界观-xxx      （蓝灯或绿灯）
===世界结束===
===事件开始===
  立即事件-xxx    （绿灯，关键字 【【xxx】】）
===事件结束===
===文风开始===
  C+C第一人称文风 （蓝灯 @D0——叙事风格指令）
===文风结束===
```

条目写作要点：

- **蓝灯条目**（constant）：无关键字。用于"每轮都必须知道"的内容：人物卡、文风、变量三件套。
  - 人物卡类 → 位置 Character After（position=1）；指令/规则类 → @D0（position=4, depth=0, role=system）。
- **绿灯条目**：写 `key` 关键字，只在关键词出现时注入。用于"少数情况才需要"的扩展设定（地点详情、NPC 档案、道具图鉴）。
- **条目长度**：单条尽量 ≤ 400 字；内容长就拆分（更利于命中率与 token 控制）。
- **逻辑条目**：把"AI 生成 NPC/地点时必须遵守的规范"（命名规则、深度要求、严禁事项）写成一条常驻条目（实测卡：`逻辑-角色生成`、`逻辑-地点生成`）——比散落的零碎要求更稳定，也让 AI 的角色生成质量可控。
- **名称即用途**：条目名（comment）用中文短语，一眼懂；机器识别的特殊条目（`[initvar]`/`[mvu_update]`）保持前缀。
- **递归**：默认 `exclude_recursion: true` + `prevent_recursion: true` 最稳（避免条目互相触发失控）。
- 想按变量动态发条目，用提示词模板 EJS（见 prompt-template.md），不要硬堆重复条目。

## 3. 变量卡的内容三联动

变量卡的好玩来自三个联动，内容构筑时就成对设计：

1. **数值 → 行为**（阶段人设）：好感度/依存度等数值分阶段改变角色行为描述（EJS 条件段、@D0）。
2. **状态 → 事件**（立即事件）：数值/状态满足条件时注入新事件（`injectPrompts` 的 `filter` + 绿灯条目 `【【事件名】】`）。
3. **状态 → 界面**（前端）：把关键数值和可交互操作呈现给玩家（状态栏/商城/任务面板）。

设计时先写一张"变量-剧情-表现"对照表（可以在回复里给用户看），再落笔：

| 变量 | 区间/状态 | 角色表现 | 触发事件 | 界面元素 |
|---|---|---|---|---|
| 依存度 | 0~20 | 回避、机械应答 | 冲动啊，请平息吧 | 进度条 |
| 依存度 | 80~100 | 黏人、话痨 | 理智啊，请不要冻结 | 进度条+提示 |
| 积分 | ≥100 | —— | —— | 商城按钮 |

## 4. 开场白与 initvar 的联动

- 保底 `[initvar]` + 每开局 `<initvar>` 块（见 mvu.md §3）：**开局的文字描述必须与初始变量一致**（开场写"好感度 15"，initvar 就必须是 15），否则 AI 会困惑。
- 技巧：先在变量管理器里调到满意的手感，复制 `stat_data` JSON，让 AI 转成 YAML 放进 initvar。

## 5. 文风条目（让 AI 文笔稳定）

一张卡的叙事质量一半靠文风条目。一个可用的模板（结构借鉴示例卡）：

```yaml
writingstyle_request:
  style_summary:
    overall_impression: 采用主要角色第一人称叙事，风格高度内省、主观，侧重感官体验与内心独白
    narration: 现在时；动作与心理描写比例约 3:7；单段不超过 4 句
    dialogue: 对白口语化、允许停顿与省略；不同角色有固定区分度的口癖
  taboo:
    - 不使用"AI 助手"式总结句、不跳出角色点评
    - 不替玩家决定行动（<user> 的行动留给玩家）
```

放在蓝灯 @D0 条目。注意：文风条目要克制——太多负面禁忌反而分散 AI 注意力。

## 6. 质量标准自查（写完卡过一遍）

- [ ] 开场 3 楼内能感受到"变量系统存在感"（状态栏变化/AI 提到数值/按钮可用）。
- [ ] 角色第一句话就对味（口癖、称呼与 mes_example 一致）。
- [ ] 变量数值变化在剧情里可被感知（不要"好感 +5"却毫无剧情痕迹）。
- [ ] 极端值有出口（好感度到顶/积分清空/角色死亡都有对应写法与事件）。
- [ ] 玩家操作有回执（前端操作写入系统日志，AI 能对玩家操作作出反应）。
- [ ] token 预算：常态上下文（世界书常驻+变量列表+规则）不超过预设的 1/3。
- [ ] 术语一致：卡内所有地方用同一种称呼（"依存度"不要有时候写"好感度"）。
