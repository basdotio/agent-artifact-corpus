# Product Model vs. Project Model

The distinction the whole book rests on.

| | Project model | Product model |
|---|---|---|
| Ideas come from | Stakeholders, down the hierarchy | The team, from customers and data |
| The team receives | A list of features | A problem to solve, with a desired outcome |
| Success is measured by | Did we ship it, on time | Did the outcome move |
| Design enters | At the end, to decorate | At the start |
| Engineering enters | At the end, to estimate | At the start |
| Validation happens | After it is built | Before it is built |
| The team is | Assembled per project, disbanded after | Durable, with its own mission |

## Root causes of failure (the project model's failure modes)

Cagan's list, and it is a checklist worth running literally:

1. Ideas descend from the hierarchy
2. The business case is built on invented numbers
3. The roadmap is organised by date and feature
4. Design is called in at the end
5. Engineering is called in at the end
6. Validation happens only after everything is built

Each one is independently diagnosable. If you find three of six, you are running a
project, not a product.

## Three contexts

The same principles, different failure mode in each:

- **Startup** — reach product/market fit before the money runs out. Everything is
  subordinate to that one clock.
- **Growth-stage** — scale without losing focus. The failure is doing more things
  worse.
- **Established** — recover the ability to innovate despite inertia and risk
  aversion. The failure is that nothing genuinely new survives the process.

Name which one you are in before diagnosing anything. The advice differs.

## Discovery and delivery

**Discovery:** find out whether it is worth building.
**Delivery:** build it well.

In parallel and continuously, never in sequence. The team is doing both every week.
