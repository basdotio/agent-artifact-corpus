## 3. 측정 방법

- 산문 추출: 마크다운에서 다음을 뺐다.
  - 코드 블록, 제목, 표, 인용, HTML, 이미지
  - front matter, import 줄, 토스의 DoDont·details 블록
- 인라인 코드와 URL: 자리표시자 `CODEX` 하나로 바꿨다. 형태소 분석기가 백틱 뒤 조사를 잘못 나누는 문제(`git rebase`를 → '르/ᆯ')를 피하려고.
- 문장 분리: Kiwi(kiwipiepy 0.24.0)의 `split_into_sents`.
- 분석 대상 문장: 다음 세 조건을 모두 만족하는 문장만 분석했다.
  - 한글이 글자의 절반 이상
  - 3어절 이상
  - 마지막 형태소가 종결어미(EF)
- 어절: 공백으로 나눈 단위 중 글자나 숫자가 든 것. 영어 단어 수와 같은 단위가 아니다.
- 지시문: 종결어미가 '-세요', '-십시오', '-시오', '-라', '-자' 등인 문장.
- '의' 사슬: 관형격 조사(JKG) 사이에 명사류만 있으면 같은 사슬로 센다. 쉼표, 그리고 '동안', '경우', '때' 같은 부사성 명사에서 끊는다.
- 명사 연속: 띄어 쓴 한글 일반·고유 명사만으로 된 어절이 이어진 수. 마지막 어절은 조사가 붙어도 된다.
  - 영문, 숫자, 코드가 든 어절과 문장부호가 붙은 어절에서 끊는다.
  - 부사성 명사에서도 끊는다.
  - 붙여 쓴 복합어는 1로 센다.
  - 고정 용어 여부는 판정하지 않는다. 규칙에서는 고정 용어를 하나로 센다.
- 절 추정: 연결어미(EC) 수 + 1. 단, 다음 연결어미는 절로 세지 않았다.
  - 보조 용언(VX) 앞: '-고 있다', '-어 주다'
  - '-지 않다/못하다'('-지는 않다'처럼 보조사가 끼어도 같다)
  - '-게 되다/하다', '-면 되다', '-어도 되다/좋다'
  - 인용 '-라고'
  - 조사처럼 쓰는 동사 뒤: '통해', '위해', '따라', '대해'
  - 형용사 뒤 부사형 '-게'
  - 관형절(ETM)과 명사절(ETN)은 따로 셌다.
- 절 추정 검증: 무작위 문장 40개의 절 수를 직접 셌다(판정자: 이 스킬을 만든 Claude 한 명).
  - 규칙을 고친 뒤 일치 37/40, ±1 이내 40/40, 평균 차이 +0.08.
  - 이 40개를 보며 규칙을 고쳤으므로, 새로 뽑은 30개로 다시 쟀다. 일치 28/30, ±1 이내 30/30.
  - '-기 때문에', '-ㄹ 때'처럼 관형형·명사형 뒤 명사로 만든 절은 연결 절에 들지 않는다.
- 표현 빈도: `kostelib.py`의 정규식. '~할 경우'는 형태소(관형형 어미 뒤 '경우')로 셌다.
  - 문장 단위 표: 분모는 분석한 문장 수다. 한 문장에 두 번 나와도 1로 센다.
  - 줄 단위 표: 분모는 코드 블록 밖의 비어 있지 않은 줄이다.

### 고치지 않아도 되는 문장에 규칙이 걸리는 사례

사람 글 묶음(toss, pre2022)에서 규칙에 걸린 문장을 25개씩 무작위로 뽑아 읽었다. 판정자는 이 스킬을 만든 Claude 한 명이다. 사람 판정자 여럿이 본 결과가 아니다.

- 설명문 17–25어절(80% 모드의 '살핌' 구간):
  - 17–21어절: 16개 중 나누는 편이 나은 문장 2개
  - 22–25어절: 9개 중 7개
  - 그래서 80% 모드에서 17어절 초과는 다른 신호가 겹칠 때만 고치게 바꿨다. 첫 기준은 '17어절이 넘으면 살핀다'였다.
- 설명문 25어절 초과: 뽑은 문장 대부분이 나누는 편이 나았다. 25어절 기준을 유지한다.
- 지시문 14어절 초과(엄격 모드): toss와 pre2022 지시문 중 16개가 걸렸다. 약 절반은 조건 하나와 동작 하나로 된 문장이었다('…를 개선하고 싶다면 … 프롬프트를 사용해 보세요'). 그래서 엄격 모드의 실제 기준은 '한 문장에 동작 하나'로 두고, 14어절은 살필 신호로 남겼다.
- 명사 연속 넷 이상:
  - 걸린 문장 대부분이 고정 용어를 포함했다: '한국어 형태소 분석 결과', '클래스 컴포넌트 생명주기 다이어그램', '슬랙 가입 요청 페이지'. 그래서 고정 용어는 하나로 센다는 예외를 두었다.
  - 첫 계측에서는 쉼표 나열('코드 예제, 명령어, 설정 방법')과 시간 명사('4년 동안')가 사슬로 잡혔다. 측정 규칙을 고쳤다.
- '의' 둘 이상: '모든 프로세스의 메모리 참조의 계획', '애자일의 방법론의 차이'처럼 실제 사슬이었다. 엄격 모드 기준(하나)에 걸리는 것이 맞다고 보았다. 첫 계측에서는 '10분의 시청 시간 동안 React의'가 잡혔다. 부사성 명사에서 끊도록 고쳤다.
- 목록 B 표현: 걸린 문장 중 정상 쓰임이 많았다.
  - '~에 대해': '각 {2, 3, 4, 5}에 대해', '프라이머리 키에 대해서만'처럼 범위를 뜻했다.
  - '~를 통해': '관계를 통해 분산된다'처럼 경로·과정을 뜻했다.
  - '~하기 위해': 대부분 보통의 목적 표현이었다.
  - '제공하다': 'API를 제공한다'처럼 실제로 갖추는 뜻이었다.
  - '진행/수행': '다음을 수행하면 됩니다', '가비지 컬렉션이 수행된다'처럼 실제 동작을 가리켰다.
  - 그래서 01-rules.md LX-3, LX-4에 '그대로 둘 때'를 표로 적었다. 이 표현들을 일괄 금지하지 않는다.

자주 나온다고 좋은 표현이라고 보지 않았다. 드물다고 나쁜 표현이라고 보지도 않았다. 위 조정은 '규칙에 걸렸지만 고칠 이득이 작은 문장'을 줄이려는 것이다.

## 6. 사전 용례로 본 직역 조합

### 방법

- 대상: 영어 have, make, pay를 직역한 조합과, 그에 대응하는 자연스러운 짝. 대조군으로 정상 기술 표현 둘을 넣었다.
- 조회 방법: 세 사전의 웹 검색 화면에서 용례 검색 건수를 셌다(`calibration/scripts/dict_check.py`).
  - 우리말샘: 찾기 결과의 '용례' 탭 건수. 구절이 포함된 용례 문장 수다.
  - 한국어기초사전: '용례' 건수. 구절이 포함된 용례 문장 수다.
  - 표준국어대사전: 자세히 찾기에서 검색 대상을 '용례'로 둔 결과 수. 문장 수가 아니라 표제어 수다.
- 활용형 처리: 검색은 부분 문자열 일치다. '내렸다'는 '내리'를 포함하지 않는다. 그래서 활용형 줄기를 여럿 검색해 더했다. 줄기끼리 겹쳐 같은 용례를 두 번 셌을 수 있다.
- 초기 검색 실험(공인 기준 아님): 우리말샘과 한국어기초사전의 검색 건수를 더했다. 독립된 문장 수나 말뭉치 빈도로 해석할 수 없다.
  - 자연스러운 짝이 20회 이상이고 직역 조합의 10배 이상이며, 표준국어대사전에 직역 조합이 없으면: 검토 후보로 표시한다. 번역투 판정이나 자동 수정으로 이어지지 않는다.
  - 둘 다 20회 미만이면: 보류한다.
  - 그 밖: 판정하지 않는다.
  - 표준국어대사전은 단위가 달라 합치지 않는다. 반대 증거를 확인하는 데만 쓴다.

## 7. 동작 시험

### 방법

- 실행: 같은 요청을 스킬 있음과 없음으로 독립 실행했다(`evals/run_evals.py`).
  - 실행마다 새 `claude -p` 세션이다.
  - 설정 파일과 MCP 커넥터를 껐다.
  - 스킬 있음: 요청 앞에 스킬 경로를 주고 SKILL.md를 따르게 했다.
  - 스킬 없음: 같은 요청만 주고 스킬을 껐다.
- 자동 채점: 본문에서 정규식으로 표면 신호를 찾는다. '확인 필요' 검사만 출력 전체를 본다. 후속 작업에서 인용 블록 뒤의 문장·코드가 잘리던 추출기를 고쳤고 저장된 출력을 재채점했다. 본문 뒤의 존댓말 알림을 본문 문체로 오판하던 경우도 고쳤다. 아래 표는 수정한 채점기로 다시 계산한 값이다.
- 블라인드 판정(`evals/judge.py`): 판정 모델은 어느 설정의 출력인지 모른다. 원문, 본문, 덧붙임만 보고 다음을 적는다.
  - 원문에 없는 사실의 추가, 사실과 범위의 누락
  - 확신 정도 변경, 의무·허용 강도 변경
  - 모호한 원문의 해석을 본문에서 하나로 고른 경우(덧붙임에서 알렸어도 실패)
  - 하나라도 있으면 '의미 보존 실패'로 센다.

- 엄격 모드에서 목록 B 표현('로그인 API에 대한')을 '범위를 정하는 말'이라며 남긴 경우가 있었다.
- 이 시험은 의미 보존만 잰다. 읽기 개선 정도를 따로 재지 않았다. 과보존과 과수정 사이의 균형은 사람 평가로 확인해야 한다.

판정기 결함 수정:

- 판정 모델은 실패 항목을 문자열이 아니라 객체(`{"원문": …, "결과": …}`)로 돌려주기도 한다. 이전 판정기는 이를 스키마 오류로 버렸다. 실패를 찾은 판정만 미판정으로 빠지므로 실패율이 낮게 집계됐다. 3회차 첫 판정에서 이 편향을 확인했다.
- 판정기는 응답 형식 오류 한 번에 남은 판정 전체를 멈췄다.
- 객체 항목을 문자열로 정규화하게 고쳤다. 응답 형식 오류는 그 건만 미판정으로 남기게 했다. 회귀 시험을 더했다. 위 수치는 수정한 판정기로 미판정 없이 다시 계산한 값이다.

### 수정본의 독립 시험

후속 작업에서는 기존 17개 개발 사례와 다른 입력 5개를 별도의 Codex 에이전트에 주었다. 한 실행은 스킬을 읽고, 다른 실행은 스킬과 기존 결과를 읽지 않았다. 결과 10개를 설정명을 숨기고 섞어 제3의 에이전트가 의미를 비교했다. 각 설정의 5개 답안은 같은 에이전트 턴에서 나왔으므로 5개의 독립 추론 세션으로 간주하지 않는다. 상세 출력·스킬 해시·판정은 [후속 검증](../../../evals/forward-2026-10-07/README.md)에 있다. 작은 사례 검토이며 독자 이해도 실험이나 Claude 재시험의 대체물이 아니다.

## 8. 한계

- 수치 기준(14, 17, 25어절 등)은 공개 문서 분포와 Claude 한 명의 판정으로 정한 작업 기준이다. 독자 이해도를 직접 재지 않았다. NIKL 56쪽의 환언 검사나 사용성 검사처럼 실제 독자에게 묻는 검증은 하지 않았다.
- 오탐 검토와 절 수 검증의 판정자는 사람이 아니다.
- 사람 글 묶음에 AI가 관여했는지 확인할 수 없다. pre2022 묶음은 시기로만 구분했다.
- 모델 비교는 Claude 세 모델, 72개 출력이다.
- 사전 조회는 웹 화면을 읽는다. 화면이 바뀌면 스크립트가 틀린 값을 낼 수 있다. 실패하면 -1을 기록한다.
- 동작 시험은 개발 사례 17개와 새 사례 4개다. 새 사례도 이 스킬을 만든 쪽이 썼다. 생성 모델과 판정 모델이 모두 Claude라 같은 계열의 편향이 있을 수 있다. 사람이 만든 정답과 대조하지 않았다.
- 후속 Codex 시험은 5개 입력뿐이다. 독립 에이전트를 사용했지만 모델 계열은 같고 시스템 지침의 영향도 남는다. 표본과 장르를 맞춘 사람 독자 평가를 하지 않았다.
- ASD-STE100 규격 원문을 읽지 않았다. STE와의 대응은 공개 설명과 2차 요약 수준이다.

uv run --no-project calibration/scripts/report.py --check
