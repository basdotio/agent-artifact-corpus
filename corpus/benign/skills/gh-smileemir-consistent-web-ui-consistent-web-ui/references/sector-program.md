# Sector extension program

Read only when authoring or reviewing a sector. This is a coverage plan, not a record of validated sectors. Each sector gets its own customer/operator page maps, component states, brand and asset rules, motion records and test paths, built on the shared workflow in SKILL.md. Do not load or present unfinished sector material as proven guidance.

## Sector gate

A sector is published as **validated** only when all four parts exist:

1. **Private research.** Study at least **five** substantial, differentiated real products, and 10–15 when business models diverge. The notes stay in a private log outside the distributable package: URL, date, observed screens and states, strengths, weaknesses, and observed-versus-inferred labels. Published files never name the studied products, and never reuse their wording, code, art, icons, branding or distinctive layouts.
2. **Five original direction briefs.** Each brief differs in customer job, brand traits, page hierarchy, product constraints, media, density and meaningful interaction, not only in palette. Each one maps the sector's routes, assets, cards, motion, a prototype gate and a failure test. Briefs are proposals; building five complete prototypes is not required.
3. **One real project.** The sector guidance has been used end to end on at least one real product (an audit and at least one approved page implemented and verified, or a new build), with evidence recorded.
4. **An evaluation set.** Realistic prompts with checkable expectations run with and without the new guidance (see `evals/` in the repository). The results show the guidance improves outcomes without wasting tokens.

Treat external research as private working evidence. A desktop page, a help article or a CSS declaration does not verify a phone interaction, a paid order, an admin screen or an animation timing.

## Evidence protocol for each studied product

Record privately: date and URL; business model and the actual task; desktop category, list and detail; phone category, filter, detail and cart at one narrow and one wider viewport; tablet or intermediate breakpoints where they matter; option changes; checkout up to the last **non-committing** public step; empty, error and recovery states; language and data conditions. A login wall, unavailable stock, a restricted region or a protected payment step is an **access limit**, not a verified screen. Pick more products if fewer than five provide the critical public evidence. Never place orders or enter payment details for research.

For each motion, record the trigger, visible start and end, device and viewport, repeat behaviour, reduced-motion behaviour, whether content was already usable, and a duration only if frames or timing data were actually captured. A CSS animation declaration does not prove it ran. Record a meaningful absence of motion too. Keep observations, official help statements and original design proposals in separate columns. Compare patterns only after five or more studies, then test the original design on real devices.

## Sequence

| Order | Sector | Decision problem to cover |
| --- | --- | --- |
| 01 | Ecommerce (in progress) | Physical, digital and configurable products; discover → decide → pay → fulfil |
| 02 | Marketplace | Two-sided discovery, seller identity, listings, trust, moderation and disputes |
| 03 | SaaS | Evaluation, onboarding, workspace roles, subscription and operational UI |
| Later | Blog and publishing, education, AI/chat products, finance, healthcare, services and booking, real estate, travel, events, developer tools, and others | Chosen after the first three with owner input and demand research |

An "other" business type is not a sector until it is named and passes the same gate. Admin dashboards are a cross-sector task family: each sector defines the roles, real data and actions it needs instead of copying a universal dashboard.

## Publishing a sector

Add only the approved sector files to SKILL.md's reference list, keep the core short, and make sure normal use loads only the sector a task needs. Mark proposals and implemented proof separately.
