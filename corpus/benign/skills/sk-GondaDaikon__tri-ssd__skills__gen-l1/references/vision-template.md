# vision.md テンプレート＋記入ガイド

gen-l1 が L1（`docs/l1_requirements/vision.md`）を生成する際の正規テンプレート。
生成前にこのファイル全体を読み、各セクションの記入基準に従うこと。
YAMLフロントマターの定義は SKILL.md 本文に従う（ここでは複製しない）。

## テンプレート全文（本文構造）

```markdown
# [プロダクト名] 要件・意思決定ドキュメント

## 1. プロダクトの意思と背景

### 1.1 解決したい課題・ペイン

### 1.2 想定ユーザー／ペルソナ

### 1.3 ビジネス上のゴール

### 1.4 原則（省略可）

迷ったときの判断基準を1〜3個。以降の全レイヤー・実装がこの原則に従う。

## 2. 制約条件・前提（省略可）

### 2.1 動作環境

### 2.2 法規制・コンプライアンス

### 2.3 外部システム連携

## 3. 要求と意思決定

### [要求名]

- **ID**: REQ-nnnn
- **優先度**: 高/中/低
- **背景・動機**: なぜこの要求が必要か。どんな課題を解決し、どんな効果を期待するか。（3-5文）

[概要説明]

**却下した代替案**（省略可）:

- [代替案] → [採用しなかった理由]

### やらないこと（スコープ外）（省略可）

- [やらないと決めたこと] → [理由]（決定日）

## 4. 体験要件（省略可）

「誰がどう使えたら成功か」の要求。実現手段（画面構成・コマンド体系等の具体仕様）は書かない（それは L2）。

## 5. 非機能要求（高レベル・省略可）

## 6. 参考・類似サービス（省略可）
```

**必須**: セクション1 (1.1-1.3), 3（各REQに「背景・動機」3-5文を含む）
**省略可能**: セクション1.4, 2, 4, 5, 6, 各REQの「却下した代替案」「やらないこと」

## セクション別記入ガイド

| セクション | 何を書く | 書かない / 判断基準 |
|---|---|---|
| 1.1 課題・ペイン | 現状の困りごとを具体的な場面つきで | 解決手段（それは REQ・L2 の領分） |
| 1.2 ペルソナ | 主要ユーザー像と利用シーンを1〜3個 | 全ユーザーを網羅する人物像設定（過剰） |
| 1.3 ゴール | 何が起きたら成功か。測れる形が理想 | 機能の列挙 |
| 1.4 原則 | 迷ったときの判断基準を1〜3個（例:「迷ったら元ファイルを壊さない方を選ぶ」） | 4個以上は優先順位が薄まる。無ければ省略 |
| 2 制約・前提 | 外から与えられた動かせない条件（動作環境・法規制・連携先） | 自分で選んだ技術（それは L2 の技術選定） |
| 3 要求（REQ） | 検証可能な要求文＋背景・動機3-5文。1プロダクト5〜20個が適正 | 機能名だけのリスト・実装手段の記述 |
| 3 やらないこと | 検討して捨てた選択肢と理由・決定日 | 検討していないことの網羅 |
| 4 体験要件 | 「誰がどう使えたら成功か」の要求（下表の観点） | 画面構成・コマンド体系等の具体仕様（L2 §3 へ） |
| 5 非機能 | 性能・セキュリティ等の高レベル要求 | 実現方式・精密な具体値（L2 で具体化） |
| 6 参考 | 参考にしたい類似サービスと参考にする点 | 競合分析レポート（過剰） |

REQ の良い例 / 悪い例:

- 良い例: 「CSV ファイルから商品を一括登録できる」＋背景・動機3-5文
- 悪い例: 「便利な登録機能」（検証不能）、「PostgreSQL の COPY で取り込む」（実装手段 → L2）

## 体験要件の書き方（product_type 別の観点）

| product_type | 観点の例 |
|---|---|
| gui | 主要導線（一覧→詳細→購入が3ステップ以内）、状態（未ログイン時も閲覧可）、迷わないための要求 |
| cli | dry-run が既定、破壊的操作は明示フラグ、エラー時は非0 exit code + stderr に原因1行 |
| api / library | 命名の一貫性、エラー応答の予測可能性、後方互換の方針 |
| batch / data | 冪等性（再実行できること）、処理フローの追跡可能性、入出力の契約 |
| doc | 対象読者、トーン（専門用語を避ける等）、分量の要求 |

いずれも「〜であること」という要求の形で書く。「〜で実現する」は L2 へ。
