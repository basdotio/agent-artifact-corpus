# L1 生成スキル

<tri_ssd_context>
Tri-SSD: L0(任意メモ docs/l0_ideas/) → L1(要件 docs/l1_requirements/vision.md) → L2(構成 docs/l2_foundation/foundation.md) → L3(フェーズ docs/l3_phases/PH-xxxx.md)。
ID形式: PREFIX-nnnn（REQ, PH, F）。番号は再利用しない（永久欠番）。
配置・分割・粒度の判断に迷ったら `${CLAUDE_SKILL_DIR}/../../docs/layer-rules.md` を読むこと。
</tri_ssd_context>

## 概要

コードからは読み取れない「なぜその要求が必要か」「なぜそのアプローチを選んだか」を記録する L1（要件・意思決定）ドキュメントを、対話または既存ドキュメント変換で生成する。

**L1 に書くのは「実現手段を1つも決めなくても真」なことだけ**（要求・成功条件・体験の要求）。技術選定・具体仕様は L2 へ。

## 生成時の原則

<avoid_over_engineering>
- 必要以上に詳細を聞き出さない（技術詳細はL2で決める）
- 「わからない」→ TODOマークして先に進む
- 機能要求は概要レベルで十分（詳細はL3フェーズ）
- 元ドキュメントにない情報を推測・捏造しない
- 体験要件・原則は省略可。無理に埋めない
</avoid_over_engineering>

## 引数

- `$ARGUMENTS` (省略可): 変換元ドキュメントパス
  - **指定あり** → 変換モード（既存ドキュメントをL1形式に変換）
  - **省略** → 対話モード（ヒアリングでL1を作成）

### 使用例

```
/gen-l1                           # 対話モード
/gen-l1 docs/existing-spec.md     # 既存ドキュメントを変換
/gen-l1 README.md                 # READMEから要件を抽出
```

## 前提処理

1. `$ARGUMENTS` があれば変換元ファイルを読み込む
2. `docs/l0_ideas/` にファイルがあれば読み込む（→ L0参照フローへ）
3. `docs/l1_requirements/vision.md` が存在するか確認（再生成モード判定）

## 出力フォーマット（必須）

### YAMLフロントマター

```yaml
---
layer: L1
product_type: cli        # gui | cli | api | library | batch | data | doc | other
updated: YYYY-MM-DD
---
```

`product_type` は成果物の種類。L2 のインターフェース仕様・L1 の体験要件の出し分けに使う。
対話モードでは Step 1 で確認、変換モードでは元ドキュメントから推定してユーザーに確認する。

### 必須構造

**生成前に `${CLAUDE_SKILL_DIR}/references/vision-template.md` を必ず読む**。テンプレート全文と、各セクションの記入基準（何を書く/書かない・REQ の良い例/悪い例・product_type 別の体験要件の観点）が定義されている。

**必須**: フロントマター、セクション1 (1.1-1.3), 3（各REQに「背景・動機」3-5文を含む）
**省略可能**: セクション1.4, 2, 4, 5, 6, 各REQの「却下した代替案」「やらないこと」

文体・構造化・機械契約マーカーの書式は `${CLAUDE_SKILL_DIR}/../../docs/writing-rules.md`（記載規約の SSOT）に従う。

## 変換モード（$ARGUMENTS 指定時）

### 変換手順

1. **元ドキュメント分析**: 構造把握、要件抽出、技術詳細とL1相当を分離
2. **product_type 推定**: 元ドキュメントから成果物の種類を推定し、ユーザーに1問で確認
3. **情報マッピング**:
   | L1 セクション | 抽出対象 |
   |--------------|---------|
   | プロダクトの意思と背景 | 概要、背景、目的、設計方針 |
   | 制約条件 | 動作環境、前提条件 |
   | 要求と意思決定 | 機能一覧、ユースケース、設計理由・方針の記述 |
   | 体験要件 | 導線・使い勝手・UX への言及（要求レベルのみ） |
   | 非機能要求 | 性能、セキュリティ等 |
4. **意図の確認**: 元ドキュメントから「背景・動機」が読み取れない要求をリストアップし、ユーザーに「なぜこの機能が必要ですか？」と確認。回答をREQの「背景・動機」に反映
5. **REQ ID付与**: 連番（下記「ID採番と保護」）
6. **不足情報**: `<!-- TODO: 要確認 -->` でマーク

### 既存L1がある場合

- **上書き**: 既存を破棄して新規作成（下記「ID採番と保護」の手順を必ず守る）
- **マージ**: 既存と変換元を統合（REQ ID継続）
- **キャンセル**: 変換を中止

## L0参照（docs/l0_ideas/ にファイルがある場合・両モード共通）

1. L0ファイルをすべて読み込む
2. アイディアの概要をユーザーに提示して確認（変換モード時は、変換元ドキュメントと重複する内容の聞き取りは省略する）
3. 各アイディアについて以下を聞き取る:
   - これはどんな課題を解決するものですか？
   - なぜこのアプローチを考えましたか？
   - 優先度は高いですか？
4. 聞き取った意図をREQエントリの「背景・動機」に反映

---

## 対話モード（$ARGUMENTS 省略時）

### 対話フロー

**Step 1: プロダクトの意思**
1. 何を作りたいですか？（プロダクト名・概要・成果物の種類 = product_type）
2. なぜ作りたいのですか？（きっかけ・課題・不満）
3. 誰のためのものですか？（ペルソナ・利用シーン）
4. 迷ったときに優先したいことはありますか？（原則。省略可）

**Step 2: 要求と意思決定**
1. ユーザーにどんな体験・価値を届けたいですか？
2. その体験を実現するために、何が必要だと考えていますか？
   - 各要求について「なぜそれが必要か」も教えてください
3. 優先度が高いのはどれですか？その理由は？
4. 検討したが「やらない」と決めたことはありますか？（→「やらないこと」へ。省略可）

**Step 3: 体験・制約・非機能（簡潔に）**
1. 使い勝手として譲れないことはありますか？（product_type 別の観点表を参考に。省略可）
2. 動作環境・特別なセキュリティ・性能要件は？
3. 参考にしたい類似サービスは？（省略可）

## 再生成モード（既存L1がある場合・対話モード時）

1. 既存ファイル読み込み、内容把握
2. ユーザーに確認：
   - **追記**: 新しい要件を追加（REQ ID継続）
   - **修正**: 既存要件を変更（影響範囲を報告）
   - **深掘り**: TODO箇所を詳細化
   - **最初から**: 既存を破棄して新規作成（下記「ID採番と保護」の手順を必ず守る）

### 保持するもの

| セクション | 理由 |
|-----------|------|
| 既存のREQ ID | トレーサビリティ維持 |

## ID採番と保護

REQ ID は共有スクリプトで採番する（採番ミス防止）:

```bash
python3 "${CLAUDE_SKILL_DIR}/../../scripts/next_id.py" REQ            # 次の1件
python3 "${CLAUDE_SKILL_DIR}/../../scripts/next_id.py" REQ --count 3  # 連続3件
```

`python3` が使えない環境（Windows の python3 は Store スタブの場合がある）では `python` / `py`。スクリプトが使えない場合は手動で: 既存REQ IDを Grep（docs/**/*.md、`_archive/` 含む）で検索 → 最大番号 + 1 → 4桁ゼロ埋め。

### 上書き・修正時の保護（必須）

既存 L1 を「上書き（最初から）」または「修正」する場合:

1. **採番は旧ファイルを破棄する前に行う**（`next_id.py` は既存ファイルを走査するため、先に消すと番号が巻き戻り、L3 の参照が別要件を指すサイレント破壊が起きる）
2. **L3 からの参照を確認**: Grep で `docs/l3_phases/` 内の `REQ-` 参照を検索し、削除・変更しようとしている REQ が参照されていたら警告する:
   「REQ-xxxx は PH-xxxx から参照されています。削除/変更すると L3 との対応が壊れます。続行しますか？」
3. 番号は再利用しない（永久欠番）。上書き後の新規 REQ も旧最大番号+1 から始める

## 完了後の案内

- 作成ファイルのパスを報告
- TODO箇所の数を報告
- 変換モード時: 抽出できなかった情報を一覧表示
- `/gen-l2` で L2 生成できることを案内

## エラーケース

| ケース | 対応 |
|--------|------|
| 変換元ファイルが存在しない | エラー: 「指定されたファイルが見つかりません」 |
| 変換元が空ファイル | エラー: 「ファイルが空です」 |
| docs/ が存在しない | 警告: 「`/init-tri-ssd` を先に実行することを推奨します」 |
| 削除対象REQがL3から参照中 | 警告: 参照元PHを提示し、続行確認 |
